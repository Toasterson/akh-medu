## Description

redb (Rust embedded database) uses single-writer locking. When one agent process writes, all other MCP calls fail with lock contention. Fix: switch to multi-reader/single-writer pattern, buffer writes, or use a connection pool. Currently blocks concurrent akhomed operations.

## Summary
The `redb` embedded database enforces single-writer locking, causing concurrent MCP agent calls to fail with lock contention. We will centralize database writes through a serialized queue or retry mechanism to safely unblock concurrent operations while preserving concurrent reads.

## Approach
Implement an actor pattern for database write operations within the agent process. Instead of having concurrent MCP tasks invoke `begin_write()` directly, route all write requests through an `mpsc` channel to a dedicated background writer task. This background task will sequentially process the queued writes against `redb` and return success or failure to the calling MCP handlers via `oneshot` channels. Read transactions will continue to execute fully concurrently by strictly using `begin_read()`. If the contention spans multiple distinct processes (e.g., multiple executor instances) rather than just async tasks within one daemon, implement an exponential backoff-and-retry wrapper around the `begin_write()` acquisition instead of an in-memory channel.

## Open questions
* Is the lock contention strictly occurring between async tasks within a single process (where an `mpsc` channel works), or across multiple distinct processes (where backoff/retry is required)?
* Do MCP write operations require synchronous confirmation of the commit, forcing callers to `.await` the oneshot channel response before proceeding?
* If contention is high and cross-process, should `redb` be replaced entirely by SQLite to natively leverage its WAL mode for concurrency?
