# [BUG] Add write timeout to engine operations blocked by daemon lock contention

## Description

When the daemon holds the agent lock for extended OODA cycles, MCP write operations (add_triple, remove_triple, persist) block indefinitely then get SIGKILL'd. Engine should use try_lock() with a configurable timeout (e.g. 5s) instead of lock() with no timeout, returning a proper error instead of hanging.\n\nThis is separate from the suspend_workspace feature — it's a defense-in-depth measure for when pause hasn't been called or doesn't release fast enough.\n\nFiles: src/engine.rs (add_triple/remove_triple paths), possibly src/bin/akhomed.rs (MCP handler timeouts)

## Summary
Prevent indefinite blocking and SIGKILLs during MCP write operations by adding a configurable timeout to engine lock acquisitions. When the daemon holds the lock for too long, operations will now gracefully fail with a structured error rather than hanging.

## Approach
Modify the `add_triple`, `remove_triple`, and `persist` functions in the engine component to use a timeout mechanism when acquiring locks (e.g., using `tokio::time::timeout(Duration::from_secs(5), lock.lock())` for async locks, or a scoped polling loop with `try_lock()` for synchronous locks). Introduce a specific error variant (e.g., `EngineError::LockContention`) that is returned when the timeout expires. Thread a configurable timeout value (defaulting to 5s) through the engine initialization path. Finally, update the MCP handlers in the daemon to map this contention error into an appropriate MCP timeout response so the client understands the resource is temporarily busy.

## Files likely to change
* `crates/anima-agent/src/engine.rs`
* `crates/anima-agent/src/bin/akhomed.rs`

## Open questions
* Are the engine locks currently synchronous (`std::sync`) or asynchronous (`tokio::sync`)? This dictates whether we use `tokio::time::timeout` or a customized `try_lock` polling loop.
* Should the 5-second timeout be injected via an environment variable, or added to the existing daemon configuration struct?
* What specific error code/format is expected by the MCP client when failing due to a busy lock, and should it include a `Retry-After` hint?

## Complexity
S: Wrapping existing locking calls with a timeout mechanism and propagating the new error to the top-level handlers is a localized change that should take less than a day.
