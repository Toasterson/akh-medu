## Phase 38 — Relocatable Session-Based Akh

**Plan:** `docs/ai/plans/2026-04-25-phase38-relocatable-akh.md`

### What this phase is

Restructures the Akh daemon so its **state lives in Postgres** and the **process is relocatable**. The daemon keeps an in-process cache (oxigraph, petgraph, HNSW(VSA), e-graph) for hot-path reasoning. Mutations are streamed to Postgres continuously (WAL-style) and full snapshots are written periodically and on deep-sleep. An Akh's identity is bound to its data, not to any particular host: when a host dies, the Akh wakes elsewhere with the same identity and resumes from the last committed mutation. Multiple Akhs share the same Postgres cluster and can collaborate via shared workspaces.

This phase does **not** make the daemon stateless — that would break the OODA loop, active inference (Phase 20), and the affective system (Phase 23). The right framing is *relocatable*, not stateless.

### Three sleep levels + continuous durability

| Level | In memory | Continuously persisted | Snapshot frequency | Wake cost |
|---|---|---|---|---|
| Running | full | every assert via WAL | every N min (e.g. 5) | 0 |
| Idle-in-memory | full | every assert via WAL | every N min | 0 |
| Deep sleep | freed | already written | full snapshot at transition | replay + HNSW rebuild |

**Crash safety**: at any moment, Postgres holds the full state up to the most recent WAL flush (seconds-old). Crash recovery replays from the latest snapshot watermark forward through the WAL. Maximum dataloss is one flush interval (target ≤5s).

Transition Idle → Deep is **on explicit signal** (host shutdown, relocation request, severe memory pressure), not timed — the warm-Akh experience stays snappy without forcing wake-cost on conversation gaps. Crash safety is independent of this transition.

### Workspace abstraction

A **Workspace** is the unit of cognitive scope:

```
Workspace = (
  active microtheory set,
  member Akh identities,
  shared goal frame,
  conversation history,
)
```

- One Akh has multiple workspaces and switches between them (browser-tab semantics)
- Multiple Akhs can be in the same workspace simultaneously (knowledge sharing, not lockstep)
- Loading a workspace = activating its microtheories on whatever daemon hosts the session
- Workspace state lives in Postgres; an Akh activating a workspace pulls its microtheories into local cache
- Phase 14 identity covers per-fact provenance — who asserted what

### Backing-store topology

```
Postgres-ha (CNPG, shared, durable)
├── seshat.*        — corpus + embeddings (already there)
├── akhomed.*       — triples (AGE), provenance, episodes, microtheories,
│                     psyche jsonb, sleep snapshots, mutation WAL
└── workspaces.*    — workspace metadata, membership, shared microtheory refs

Akh daemon (relocatable, hosted on Talos / 7900 XTX / M2 / RPi)
├── In-memory: oxigraph cache, petgraph index, HNSW(VSA), e-graph
├── Local disk: HNSW(VSA) cache for same-host fast wake (single-writer per host)
├── WAL flush: every assert/retract → akhomed.mutation_log (N-second batch)
├── Snapshot: every M min + on deep-sleep signal → akhomed.snapshots
└── Boot: replay last snapshot + WAL tail from Postgres + rebuild HNSW
```

### Continuous durability protocol

- Every assertion / retraction / microtheory-change is appended to an in-process WAL buffer
- WAL buffer flushes to `akhomed.mutation_log` (Postgres) every N seconds *or* M asserts (whichever first); target ≤5s flush interval under normal load
- Periodic full snapshot (every ~5min) bounds replay distance; truncates the WAL behind the watermark
- On wake/recovery: load latest snapshot, then replay any mutations newer than the snapshot watermark
- The watermark + WAL is what makes this crash-safe with bounded dataloss, *independent* of the sleep-level transition

### HNSW wake protocol

- HNSW(VSA) is **in-process only** — never persisted to Postgres
- On same-host wake: read HNSW from local-disk cache (sub-second)
- On cold/relocated wake: rebuild from `akhomed.facts` (~hundreds of ms for 10K vecs, ~30–60s for 1M vecs)
- Rebuild is the wake-latency budget; if a workload exceeds it, we measure and tune (Phase 40 territory if e-graph hits the same wall)
- **No cross-process sharing of the disk cache**: akhomed runs alone per host/container in production. Single-writer per host. No advisory-lock layer at the disk-cache boundary.

### Split-brain protection on relocation

Two operators wake the same Akh on two hosts simultaneously, possibly with clock skew. Mitigation is **layered**:

1. **`last_seen` watermark** (epistemic guard): an Akh writes a heartbeat into `akhomed.akhs.last_seen` every flush interval. A new wake aborts if `last_seen` is more recent than the relocation grace window (default 30s).
2. **Postgres advisory lock** (mechanical guard, hard requirement): keyed on `akh_id`, taken before any state mutation. Survives clock skew that would otherwise fool `last_seen`. Released on graceful shutdown; auto-released on connection drop.

Both must succeed for an Akh to enter Running state.

### AGE for outside-the-Akh read

Akhs work on in-process oxigraph (fast, single-writer). AGE views over `akhomed.facts` give *other* applications query access to the graph (read-only) without needing to talk to the Akh daemon at all. Cypher consumers (visualizers, external tools) plug in here.

**AGE availability is guaranteed by deploy-side commitment.** The homelab CNPG image is built with AGE + pgvector pre-baked at known versions (separate ticket on the homelab side). AGE is still treated as a *projection over* `akhomed.facts` so that a future migration off AGE doesn't lose Akh state — but the runtime risk of "AGE goes missing" is effectively zero.

### Idempotent batched writes

- Asserts are content-addressed and deduplicated at the cache boundary
- Read-heavy workload assumed; only dedicated jobs write back
- Write-back to Postgres is batched on a flush trigger (every N seconds or M asserts, whichever first)
- Assertion idempotence means we can safely retry batched writes on transient failure
- Same idempotence makes WAL replay safe (re-applying mutations is a no-op past the first)

### Multi-Akh sharing

- **Shared homeserver**: two Akhs on the same akhomed in the same workspace see each other's assertions live (both reading the same Postgres rows). Messaging via `AgentProtocolMessage` for active coordination.
- **Cross-homeserver**: Phase 36 delegation protocol covers Akh ↔ Akh across networks. Workspace contents replicate via `.akhskill`-style archives (Phase 31) for off-network sync.

### Akh-to-host binding

- Akhs are statically stuck to one akhomed by default
- Migration is a **recovery** mechanism (host dies → wake elsewhere with same identity), not routine load-balancing
- Default home: M2 in cellar (when deployed) hosts most Akhs; cluster hosts the always-on primary that Claude talks to
- 7900 XTX desktop is *not* an Akh host — it's an inference backend that any Akh can route to (see Phase 39)

## Summary
Restructure the Akh daemon to be safely relocatable by persisting its state via a Postgres Write-Ahead Log (WAL) and periodic snapshots, unbinding its identity from any specific host. This introduces a three-tier sleep state machine (Running, Idle, Deep) and a "Workspace" domain concept while utilizing Postgres advisory locks and AGE-based graph views to ensure safe crash recovery and external observability.

## Approach
To transition the Akh daemon to a relocatable, Postgres-backed architecture, we will expand `anima-core` and `anima-proto` with new `Workspace` and Akh identity structures. In `anima-db`, we will introduce the `akhomed.*` schema via a new migration, creating tables for the continuous mutation WAL, periodic snapshots, Postgres AGE graph triples, workspaces, and robust split-brain prevention mechanisms utilizing both a `last_seen` timestamp and a Postgres advisory lock keyed by `akh_id`. The host-side daemon in `anima-agent` will be refactored to incorporate a three-tier sleep state machine (Running, Idle-in-memory, Deep sleep) and an in-process WAL buffer that streams assertions back to Postgres in batched, idempotent flushes. Finally, we will build out the wake-and-recovery protocol in `anima-agent`, allowing a waking process to recreate its cognitive state by reading the latest snapshot, replaying unapplied WAL mutations, and rapidly rebuilding its HNSW index from a local disk cache.
