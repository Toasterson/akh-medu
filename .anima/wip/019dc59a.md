## Phase 40 — E-graph Persistence

**Plan:** `docs/ai/plans/2026-04-25-phase40-egraph-persistence.md`
**ADR:** `docs/ai/decisions/051-egraph-persistence.md`

### What this phase is

Decides whether the e-graph (egg saturation product over facts + rules) needs to be persisted at all, and if so, what shape. Today the e-graph is a derived structure — it's regenerated by re-running rules over facts during reasoning. The Phase 38 wake protocol assumes this regeneration is fast enough; if it isn't, we cache the saturation product across deep-sleep boundaries so wake doesn't pay re-saturation latency.

This phase is structured as **measure-and-decide** rather than build-and-ship: we instrument first, choose based on data.

### Three candidate persistence shapes

| Option | What's stored | Pros | Cons |
|---|---|---|---|
| **(0) Nothing** | Re-saturate on wake | Simplest, no staleness risk | Could be slow on large theories |
| **(1) Class roots only** | Canonicalized e-class roots + bindings | Smaller than full state, regen cheaper | Still some wake cost; canonicalization complexity |
| **(2) Full state** | Complete e-graph with rewrites | Fastest wake | Largest snapshot, hardest to invalidate |

Default heading is (0) until measurement says otherwise.

### Measurement plan

Build a benchmark harness that:
1. Generates synthetic theories of varying size (10², 10³, 10⁴, 10⁵ facts × small/medium/large rule sets)
2. Saturates the e-graph from cold
3. Records: time-to-saturation, e-class count, memory peak
4. Repeats for the actual KGs of representative live Akhs (with anonymized snapshots)

The harness exposes a `--what hnsw|egraph|both` flag so the same tool also covers HNSW(VSA) rebuild measurement on the wake path. Both rebuilds happen on wake; sharing the harness means we get a unified wake-budget number rather than two separate ones.

### Decision criteria

- If saturation < 5 s for typical theories → Option (0). E-graph is purely derived.
- If saturation 5–30 s for typical theories → Option (1). Persist canonicalized roots.
- If saturation > 30 s for typical theories → Option (2). Full persistence.

### If we persist: invalidation semantics

The persisted form is **derived from facts + rules**. Both can change between sleep and wake. Invalidation triggers:

- Microtheory schema change (rule added / removed / rewritten)
- Fact added/retracted that's referenced by the persisted e-graph
- Egg version bump (the saturation product format is implementation-dependent)

On any trigger: discard cached state, re-saturate from facts.

### Key deliverables

- Benchmark harness for e-graph saturation across varying theory sizes
- `--what hnsw|egraph|both` flag covering HNSW rebuild measurement in the same tool
- Measurement report: time-to-saturation distributions for synthetic + real-world KGs
- ADR documenting the decision: which option, why
- Implementation of the chosen option (only if (1) or (2) wins)
- Invalidation protocol if persistence is chosen

### Dependencies

Phase 38 (Relocatable Akh) — provides the snapshot/replay framework that this hooks into (or doesn't, if Option 0 wins).

### Why this priority

Wake latency is a UX concern, not a correctness concern. Doing this *after* Phase 38 ships and we've measured real workloads is the right order — premature optimization here means we'd persist e-graph state that turns out to take seconds to rebuild, paying complexity cost for no benefit.

## Summary
Measure the latency of E-graph saturation and HNSW rebuilds from cold start to determine the appropriate persistence strategy for the Relocatable Akh wake path. Build a benchmark CLI to test wake costs across varied theory sizes, author an ADR based on the results, and optionally implement cache persistence and invalidation logic.

## Approach
Introduce a new CLI benchmark harness (`wake_bench`) with a `--what hnsw|egraph|both` flag to measure rebuild costs. The harness will generate synthetic knowledge graphs ranging from 10² to 10⁵ facts against varying rule sets, and also load anonymized snapshots from real-world Akhs. It will record time-to-saturation, e-class counts, and peak memory. Once data is gathered, compile a measurement report and draft ADR 051 to codify the persistence decision. If saturation times mandate Option 1 (class roots) or Option 2 (full state), implement the chosen serialization (likely CBOR for cross-architecture portability) within the core logic, along with cache-invalidation triggers tied to schema changes, fact modifications, or engine version bumps.

## Open questions
* Are there active inference workloads where partial e-graph state is needed mid-cycle, requiring incremental state persistence?
* Should persistence happen at the per-microtheory granularity or be scoped at the entire per-Akh level?
* Will cross-architecture snapshots strictly standardize on CBOR for x86/M2 compliance, or does bincode remain viable if speeds heavily lag?
* What is the mechanism for sourcing and injecting the "anonymized snapshots of real KGs" into the new benchmark harness?
