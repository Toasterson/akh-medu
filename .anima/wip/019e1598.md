# [HIGH] redb single-writer lock blocks concurrent MCP tool calls on same workspace

## Description

MCP calls to agent_psyche and agent_goals fail with: 'failed to open workspace tecton: redb transaction error: Database already open. Cannot acquire lock.' Status tool works (single write + quick release) but agent tools hold the lock longer. The redb store is single-writer, so any overlapping tool call fails. Impact: can't query psyche, goals, or episodic memory through MCP while status is held or another agent tool is in flight. Fix: implement workspace-level mutex/semaphore, or switch to a multi-reader store (SurrealKV, or redb with write-through caching layer).

## Summary
Concurrent MCP tool calls fail because `redb` enforces an exclusive lock at the file level, causing "Database already open" errors when multiple tool invocations attempt to connect simultaneously. The fix will centralize the `redb` database connection into a single shared instance or introduce retry logic with exponential backoff to handle lock contention gracefully.

## Approach
Implement a centralized database connection manager struct (e.g., a workspace store wrapper) that holds an `Arc<redb::Database>`. Update the MCP server initialization to create or open this database exactly once at startup, and pass the `Arc` down to the context of individual MCP tools like `agent_psyche`, `agent_goals`, and `status`. Audit the tool handlers: ensure any tools that do not mutate state (e.g., retrieving goals or psyche) explicitly call `begin_read()` on the shared database instance, which allows concurrent readers, instead of inadvertently acquiring an exclusive write transaction. If tools are strictly spawned as separate OS processes rather than internal async tasks, implement an exponential backoff retry loop on the database open call or migrate to a daemon-based multiplexer.

## Open questions
*   Are `agent_psyche` and `agent_goals` invoked as concurrent asynchronous tasks within a single long-lived process (like `anima-exec`), or do they run as completely isolated ephemeral processes?
*   Do the failing tools actually need to mutate workspace state, or were they simply using `begin_write()` when `begin_read()` would suffice?
*   If we must serialize writer access across separate processes, would migrating to a backend like surrealKV or SQLite be more robust long-term than managing a local IPC daemon or relying on sleep/retry loops?

## Complexity
M: 1-3 days. Sharing an `Arc<Database>` in a single async space and auditing read/write transactions is a lightweight (S) task. However, if the architecture currently relies on multi-process ephemeral operations requiring IPC serialization or a swap of the underlying storage backend, the effort pushes into medium complexity.
