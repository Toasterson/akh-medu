## Description

Knowledge about the home cluster (11 nodes, Talos Linux, FluxCD, storage topology) is stored as flat descriptive strings: 'cluster nodes headnode stor01 stor02 stor03 wk01 wk02 wk03 wk04 wktiny01 wktiny02 wktinystor01' and '83.77.127.23 public IP' are single flat entities. Schema exists (K8sNode, IP, state, K8sNode->IP->100.98.169.36) but is sparsely populated. The agent has the data but can't query 'which nodes are NotReady' or 'show me storage node topology' without the text being parsed into structured triples. Fix: ingest text descriptions through NLU pipeline to produce structured K8sNode/StorageClass/State triples.

## Summary
Update the agent knowledge ingestion pipeline to parse flat Kubernetes cluster topology text strings into structured ontology triples. This enables agents to query structured relationships and states natively (e.g., node readiness, storage topologies) instead of relying on opaque text blobs.

## Approach
Implement an NLU extraction pipeline in `anima-ai` utilizing Gemini via OpenRouter. A few-shot prompted LLM call will ingest flat text topology descriptions and output structured JSON extracting `K8sNode`, `StorageClass`, `State`, and `IP` entities and their relationships. We will add the core domain types representing these ontology triples to `anima-core`, and add database operations to `anima-db` to store them. Finally, wire the extraction step into `anima-server`'s agent or knowledge ingestion services to automatically parse descriptions upon ingest. 

## Files likely to change
* `crates/anima-ai/src/extract.rs` (new, to handle NLU extraction)
* `crates/anima-ai/src/prompts.rs` (to define the ontology extraction few-shot prompt)
* `crates/anima-core/src/domain/agent.rs` (to add types for structured ontology schema)
* `crates/anima-server/src/services/agent.rs` (to trigger extraction when the cluster context is updated)
* `crates/anima-db/src/repo/agent.rs` (to insert/upsert the extracted triples)
* `crates/anima-db/migrations/NNN_create_ontology_triples_tables.sql` (if the sparse schema requires new tables)

## Open questions
* **Trigger Mechanism:** Should the NLU extraction step run synchronously and block the ingestion HTTP/gRPC request, or process asynchronously in a deferred worker?
* **Backfill:** Do we need a one-off database migration or script to retroactively process existing flat strings currently stored in the system?
* **Conflict Resolution:** If the LLM extraction yields triples that conflict with already populated structured properties or ground truth, do we overwrite the existing state logically, or flag it for human review?
* **Ontology Strictness:** Do we enforce a strict predefined enum for relationships (e.g., `HasIP`, `AssignedTo`, `InState`) or allow dynamic generation by the model?

## Complexity
M: 1-3 days. Integrating the standard OpenRouter/Gemini call is straightforward, but prompt tuning for properly normalized, hallucination-free JSON outputs and smoothly wiring the graph inserts into the sparse schema will require iteration.
