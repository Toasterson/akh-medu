## Description

## Symptom

Every chart upgrade for `akh-medu` since seshd was deployed has hit the same deadlock:

1. helm-controller patches the seshd Deployment with the new image / chart version.
2. Kubernetes rolling-update strategy schedules a NEW pod *first*, which tries to mount the `seshd-models` PVC (`ReadWriteOnce`).
3. The OLD pod still has the PVC mounted on its node.
4. New pod stays `Init:0/1` with `MountVolume.SetUp failed ... verifyMount: device already mounted`.
5. helm-controller waits, eventually `context deadline exceeded`, marks `UpgradeFailed`.
6. Operator (me) intervenes: `kubectl delete pod <old>`, `kubectl scale deploy --replicas=0`, then re-trigger Flux. Sometimes also a manual `helm upgrade`.

Observed on chart 0.1.2 → 0.1.3 (yesterday) and 0.1.3 → 0.1.4 (today). It will keep happening on every upgrade until something changes.

## Two clean fixes

### (a) `strategy: Recreate` on the seshd Deployment

Trade rolling-update zero-downtime for serialised teardown. Old pod terminates fully (PVC released) before the new one starts. ~30 s of downtime per upgrade — acceptable for a service that's behind a single-replica RWO PVC anyway and isn't yet user-facing.

Chart change: `charts/akh-medu/templates/seshd-deployment.yaml` adds `spec.strategy.type: Recreate`. One-liner; no values changes needed.

### (b) Eliminate the PVC entirely via OCI model bootstrap

Tracked separately in WI `019dbc03`. Once seshd pulls models from `oci://code.aopc.cloud/toasterson/model-*` into an `emptyDir` at startup, the deployment is stateless and rolling updates Just Work. This is the better long-term answer because it also fixes the manual-bootstrap pain (today every fresh install needs `kubectl cp` of `model.onnx` and `tokenizer.json`) and it lets seshd scale beyond one replica.

## Recommendation

Ship (a) **now** as a stop-gap (4-line chart change, ships in next chart bump) so the deploy loop stops fighting back, and let (b) play out at its own pace. Once (b) lands, drop the `Recreate` strategy and we're back to default rolling.

## Summary
The `seshd` deployment currently fails during chart upgrades because the default rolling update strategy conflicts with its ReadWriteOnce (RWO) persistent volume. This will be fixed by temporarily overriding the deployment strategy to `Recreate` to ensure the old pod releases the PVC before the new pod attaches, acknowledging a brief ~30s downtime per upgrade.

## Approach
Modify the `seshd` Deployment manifest in the Helm chart to specify `spec.strategy.type: Recreate` so that Kubernetes terminates the old pod fully before scheduling the new one. This override should be conditionally gated on `seshd.persistence.enabled` or `seshd.models.enabled` if applicable to the existing chart structure. Following this, bump the chart version in `Chart.yaml` to `0.1.5` and update the chart's `README.md` to document the expected transitional downtime behavior for future operators.
