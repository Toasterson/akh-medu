## Description

## Why this exists

Phase 38 (`019dc599-81c5`, *Relocatable Session-Based Akh*) puts triple data into AGE-backed Postgres tables and depends on the AGE extension being reliably present in production. AGE is upstream-maintained by Apache; CNPG (CloudNativePG) doesn't bundle it by default. Stock CNPG images carry pgvector but not AGE.

Resolution: we build our own CNPG image — a thin wrapper around the upstream CNPG image that adds the AGE extension at a known version. The image is published to the same OCI registry that hosts seshd / akh-medu chart artifacts, and the homelab `postgres-cluster.yaml` is updated to use it.

This is filed under the akh-medu project because it's a hard dependency of Phase 38, but the actual deliverable lives in the homelab Flux repo (`~/ws/homelab` / `ssh://git@github.com/toasterson/talos`). When a homelab-specific Anima project exists, this should be moved.

## What ships

1. **Dockerfile**: small multi-stage build inheriting from the upstream CNPG image (`ghcr.io/cloudnative-pg/postgresql:<X>`), with AGE `apt install` (or build from source if the apt package lags). Pinned versions for both Postgres major and AGE.

2. **CI workflow on the homelab repo**: builds + pushes the image on every change to `images/cnpg-with-age/`. Tags with the AGE+CNPG version pair (e.g. `:16.4-age1.5.0`). Also tags `:latest` for development convenience.

3. **`postgres-cluster.yaml` update**: `imageName` field swaps from the upstream image to the custom one.

4. **Smoke test**: a startup script verifies `CREATE EXTENSION IF NOT EXISTS age` + `CREATE EXTENSION IF NOT EXISTS vector` both succeed during init. Image build fails if they don't.

5. **Migration safety**: existing CNPG cluster's data must not be lost on the image swap. CNPG handles in-place image updates via rolling restart; document the change procedure in the homelab repo's README.

## Why this priority

Phase 38's AGE-projection schema cannot land until the cluster reliably has AGE. Without this, Phase 38 deploys to staging and discovers AGE is missing. With this, the deploy path is straightforward.

## Edge cases worth nailing down before implementation

- AGE versioning: AGE has had abandoned releases historically. Pin to the latest stable release that the upstream Postgres major supports. Document the upgrade path.
- CNPG `imageName` change as part of an upgrade (not a fresh install): test that the rolling restart preserves data and that the AGE extension can be created post-restart on the existing database.
- Talos cluster runtime: confirm the AGE binaries don't depend on glibc symbols that the Talos minimal-runtime container lacks. (CNPG's base image is already Talos-compatible, so likely fine, but worth double-checking.)
- AGE vs Postgres: AGE upstream tracks specific Postgres majors. If we want PG 17 we need to verify AGE supports PG 17 before committing.

## Summary
Create a custom CloudNativePG Docker image containing the Apache AGE and pgvector extensions to satisfy database dependencies for Phase 38. Create a CI/CD pipeline to build and publish this image, and update the existing homelab deployment manifests to consume the new image.

## Approach
Create a new `images/cnpg-with-age` directory in the external homelab repository containing a multi-stage Dockerfile that inherits from `ghcr.io/cloudnative-pg/postgresql`. Within the Dockerfile, install build dependencies, fetch the Apache AGE source corresponding to the target PostgreSQL major version, compile, and install the extension alongside the pre-existing `pgvector`. Add a startup script to the image to smoke test the presence of both extensions via `CREATE EXTENSION` commands. Setup a GitHub Actions workflow to build and push this custom OCI artifact upon directory changes. Finally, update the `imageName` in the cluster's `postgres-cluster.yaml` to point to the new image, verify the rolling restart succeeds without data loss, and document the upgrade procedure in the repository's README.
