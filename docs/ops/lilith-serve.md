## What it is

One Runpod pod, `akh-medu-lilith-serve` (EU-FR-1, 1x H100 80GB, network volume `c6kdciozex`),
serves Lilith through vLLM's OpenAI API with served model name `lilith`. The pod is created
once and afterwards only **stopped and started**. The `lilith` akh points its
`chat_backing = "openai"` at the pod's proxy URL.

Runpod serving is a **test surface** (operator decision 2026-09-27). Everyday serving moves to
the local RTX 3090 / RX 7900 XTX once they qualify (C6b). The supervisor enforces these limits:

| Limit | Value | Enforced by |
|---|---|---|
| Session length | at most 2 h, shorter when the budget below is nearly used | `idle-watch` (session cap); on-pod backstop at 2 h 10 min |
| Idle | stop after 20 min without a request | `idle-watch` (vLLM `/metrics` counters and in-flight gauges) |
| Weekly | at most 6 GPU-hours (ISO week, Monday 00:00 UTC) | `start` refuses; the session cap shrinks to the remainder |
| Monthly | at most 25% of the credit available to serving this month = 25% × (current balance + serving spend so far this month); top-ups raise it, training spend lowers it | `start` refuses; the session cap shrinks |
| Reserve | never start into the last $5 of credit (training has priority) | `start` refuses |
| Minimum | a start that could not last 10 min is refused | `start` |

A refusal names the binding limit, the usage, and when it resets.

## Stop/start keeps the URL — with one caveat

Verified against the Runpod docs on 2026-09-28:

- The proxy URL is `https://[POD_ID]-[INTERNAL_PORT].proxy.runpod.net`
  ([Expose ports](https://docs.runpod.io/pods/configuration/expose-ports)). It is a function of
  the pod id only.
- `POST https://rest.runpod.io/v1/pods/{podId}/stop` and `.../start` stop and resume the **same
  pod** ([Manage Pods](https://docs.runpod.io/pods/manage-pods),
  [StartPod API](https://docs.runpod.io/api-reference/pods/POST/pods/podId/start)). Stopping
  releases the GPU and keeps `/workspace`; the container disk is wiped. So the id, and with it
  `https://<podId>-8000.proxy.runpod.net`, is **stable across stop/start**.
- **Caveat: GPU availability on resume is not guaranteed.** A stopped pod stays tied to its
  physical machine. If another tenant rents that machine's GPU meanwhile, the pod resumes with
  **zero GPUs** ([Zero GPU Pods](https://docs.runpod.io/pods/troubleshooting/zero-gpus)).
  `lilith_serve.py start` detects `gpu.count == 0`, stops the pod again (exit 4) and names the
  options: retry later, or `recreate`. `recreate` terminates the pod and creates a new one on the
  same network volume. That is the **only** path that changes the pod id and therefore the URL.
  It rewrites the 1Password endpoint item and prints `BASE URL CHANGED`. The `lilith` akh's
  `base_url` must then be updated.
- When the account balance reaches $0, Runpod stops pods that have a network volume attached
  ([Network volumes](https://docs.runpod.io/storage/network-volumes)). The idle-watch notices the
  external stop and closes the session.

## One-time setup (supervisor)

Prerequisites: this PR is merged; the operator has approved the create; the Mac's SSH public key
is registered on the Runpod account (the image's `/start.sh` installs it, as in C6); no training
pod on the same volume is mid-run with a different env lock (see "Shared env" below).

```sh
# 0. From a CLEAN origin/main checkout (deploy-from-main rule).
git -C ~/ws/akh-medu fetch origin && git -C ~/ws/akh-medu checkout --detach origin/main
S=~/ws/akh-medu/scripts/lilith/serve/lilith_serve.py
PY=/opt/homebrew/bin/python3            # 3.11+; /usr/bin/python3 is 3.9

# 1. Budget and credit first.
$PY $S ledger

# 2. Create the pod (billable, starts it; generates + stores the serve key; records the endpoint).
$PY $S create --yes                      # --kv-cache-dtype fp8 | --key-source runpod-secret: see below

# 3. Build the payload from origin/main and install it. The pod verifies every file against the
#    manifest and the main SHA; the Mac checks `merge-base --is-ancestor <sha> origin/main` first.
bash ~/ws/akh-medu/scripts/lilith/runpod/make_payload.sh ~/lilith-private/serve/payloads
$PY $S install-payload ~/lilith-private/serve/payloads/lilith-payload-main-<sha12>.tar.gz --launch

# 4. Wait for vLLM (~8 min model load; +~5 min when the env is rebuilt from a new lock).
$PY $S wait-ready

# 5. Keep the idle-watch running: the LaunchAgent (below), or `$PY $S idle-watch` in a terminal.
```

From then on, every pod start runs `serve_pod.sh` from `serve/current` automatically (the pod's
start command), so step 3 is needed again only for a new payload.

### LaunchAgent for the idle-watch

```sh
sed -e "s#__HOME__#$HOME#g" -e "s#__REPO_ROOT__#$HOME/ws/akh-medu#g" \
    -e "s#__PYTHON_BIN__#/opt/homebrew/bin/python3#g" -e "s#__LOG_DIR__#$HOME/Library/Logs/akh-medu#g" \
    deploy/lilith/it.akh.lilith-serve-idle.plist.template > ~/Library/LaunchAgents/it.akh.lilith-serve-idle.plist
mkdir -p ~/Library/Logs/akh-medu
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/it.akh.lilith-serve-idle.plist
launchctl print gui/$(id -u)/it.akh.lilith-serve-idle | grep -E 'state|last exit'
```

`idle-watch --daemon` runs permanently. Between sessions it reads only local state, plus one
Runpod status call every 15 min. That call adopts a pod started from the console, so it is
supervised too. **Skipping it** means a started pod bills until the on-pod backstop stops it at
2 h 10 min (about $7.60 per forgotten session).

## Everyday use

```sh
$PY $S start            # budget check -> resume -> zero-GPU check -> wait for /health; prints stop_by
$PY $S start --watch    # the same, then idle-watch in the foreground (without the LaunchAgent)
$PY $S status --json    # pod state, GPUs, session elapsed/cap/idle, health, usage

```

Report the spend from `ledger` with every run report (ADR 116: the supervisor reports spend).
The ledger counts serving only, at the pod's `costPerHr` (default $3.49/h). Volume storage and
training are billed separately.

## Adapter or frozen parent

- **Default (Stage 0): the frozen parent.** There is no `adapters/active/active.json`.
- **A certified adapter** is served only when C4b `AdapterRegistry.load_active` accepts it: an
  operator acceptance embedded in the manifest and on record, and the adapter bytes hashing to the
  pinned `adapter_sha256`. vLLM then serves the base as `lilith-parent` and the adapter as
  `lilith`, so the akh config does not change.
- **A present but invalid `active.json` is a refusal** (`lilith::serve::adapter_uncertified`),
  never a silent fallback. The options are named in the error: restore the bytes, move
  `active.json` aside, or start once with `LILITH_SERVE_ADAPTER=parent` (recorded in
  `session.json`).

## Tool calling

The `lilith` akh uses native OpenAI `tool_calls`, so the pod never serves without them.

- **Start-up (`serve_pod.sh` → `serve_tools.py resolve`).** Runs `--enable-auto-tool-choice
  --tool-call-parser <p> --chat-template <t>`. The parser is resolved against the installed
  vLLM: `ToolParserManager` (`vllm.tool_parsers`, or `vllm.entrypoints.openai.tool_parsers` on
  older releases; eager plus lazy names). If that module can't be imported, the parser comes from
  the `--tool-call-parser {…}` choices in `vllm serve --help`.
  - `LILITH_SERVE_TOOL_PARSER=auto` (the default) picks `gemma4`, vLLM's Gemma 4 parser
    (`Gemma4EngineToolParser`, native `<|tool_call>call:…` syntax), when it is registered.
  - An explicit name is used only if it is registered.
  - Anything else is a refusal (`lilith::serve::tool_parser`) listing the available parsers.
    `pythonic` (vLLM's Gemma 3 choice) is **never auto-selected**: it only parses calls produced
    by a pythonic template, which the pinned parent template is not.
- **Chat template.** `--chat-template` is the parent's pinned `chat_template.jinja`
  (`LILITH_SERVE_CHAT_TEMPLATE` overrides it); it must exist. The parser, how it was chosen, the
  registry source, the available names, and the template path and sha256 are recorded under
  `session.json` → `tool_calling`.
- **Readiness (`start`, `wait-ready`).** After `/health`, one chat request with a trivial
  `get_time` tool (`tool_choice: auto`, temperature 0):
  - a well-formed `tool_calls` entry records `tool_calling: verified`;
  - a plain-text answer records `unverified` with the raw `finish_reason`;
  - an HTTP error, a malformed call, or native call syntax left unparsed in `content` is exit 6
    (`lilith::serve::tool_calling`). Under `start` the pod is stopped.

  The record is in `state.json` and `~/lilith-private/serve/readiness/<session>.json`.

### Reasoning parser

Gemma 4's pinned chat template opens a `<|channel>thought` block whenever tools or a system
message are present — which is always, for Lilith. Without `--reasoning-parser`, vLLM has nowhere
to route that channel except into the answer's `content`, so the raw `<|channel>thought\n…\n
<channel|>` markers leak straight into what the akh sees and shows.

- **Start-up (`serve_pod.sh` → `serve_tools.py resolve-reasoning`).** Resolved the same way as the
  tool-call parser, against `ReasoningParserManager` (`vllm.reasoning`, or
  `vllm.entrypoints.openai.reasoning_parsers` on older releases; eager plus lazy names) — there is
  no help-text fallback here, since `vllm serve --help` prints `--reasoning-parser
  REASONING_PARSER` with no enumerable choice set.
  - `LILITH_SERVE_REASONING_PARSER=auto` (the default) picks `gemma4` when it is registered.
  - An explicit name is used only if it is registered; otherwise a refusal
    (`lilith::serve::reasoning_parser`) listing the available parsers.
  - `LILITH_SERVE_REASONING_PARSER=none` disables reasoning-channel capture outright, with no
    registry lookup at all.
- **Non-fatal, unlike tool calling.** `auto` with nothing registered (including the common
  off-pod case where `vllm.reasoning` isn't importable at all) quietly disables reasoning capture
  instead of refusing to serve: a leaked thinking channel is ugly, not a broken response, so the
  pod still comes up without `--reasoning-parser`. Only an *explicit* unregistered name refuses —
  a stated request that can't be honored is a misconfiguration worth failing loudly on.
- **Record.** The parser (or `null` when disabled), how it was chosen, the registry source and the
  available names are recorded under `session.json` → `reasoning`.
- **akhomed side.** The `openai` backend routes a streamed `delta.reasoning_content` (or
  `reasoning`) to the reasoning/thinking channel (`src/agent/openai_backend.rs`, `chat_stream`).
  The non-streaming path reads `message.reasoning_content` / `message.reasoning` into
  `AssistantTurn::reasoning`; the agentic loop emits it as a thinking step (`AkhMessage::Reasoning`)
  ahead of the answer, never merged into the visible content and never replayed to the model
  (Anima WI 01a0e270-314e).

## KV cache dtype

`auto` (the default) is bf16. Gemma 4's KV is small: 0.60 GB per sequence at 32K (local GPU
qualification §2a), so there is no memory reason to quantize on the H100. `fp8`, `fp8_e4m3` and
`fp8_e5m2` halve the KV memory; use them for many parallel rollouts. **int8 is refused**: it is
not a vLLM KV cache dtype. int8 or TurboQuant-class KV belongs to the local-card lane (C6b).
The dtype comes from the pod env `LILITH_SERVE_KV_CACHE_DTYPE`, set at create time
(`--kv-cache-dtype`). Changing it later means editing the pod env in the console, which resets
the container.

Numerics: `LILITH_NUMERICS_SDPA_BACKEND=efficient` + `..._MATH_FALLBACK=1` (the C6 round-3 CUDA
default) is exported for torch paths. vLLM picks its own attention kernels and is outside the C6
cache control; `session.json` records this.

## Privacy

- vLLM's request logger stays off: vLLM ≥ 0.10 needs `--enable-log-requests`, which is never
  passed; older releases get `--disable-log-requests`. The choice is recorded in `session.json`.
- `log_redact.py` is the second line of defence. Every line of vLLM output is timestamped. Lines
  that carry request bodies (`Received request … prompt: …`, `prompt_token_ids`, …) become
  `[redacted: request body] id=<request id>`. The API key is replaced, and lines are capped at
  2,000 chars.
- What remains is the request log: uvicorn access lines (time, method, path, status) plus vLLM
  throughput stats.

## Failure modes

| Symptom | Meaning | Action |
|---|---|---|
| `start` exit 3 `lilith::serve::budget` | A limit binds (message names it and the reset) | Wait for the reset, ask the operator to top up, or serve locally (C6b) |
| `start` exit 4 `lilith::serve::zero_gpu` | The pod's machine has no free H100; the pod was stopped again | Retry later, or `recreate --yes --confirm-terminate <podId>` (operator-approved; new URL) |
| `start`/`wait-ready` exit 6 `lilith::serve::tool_calling` | The tools request failed, or returned a malformed or unparsed call; `start` stops the pod | Check `session.json` → `tool_calling` and the vLLM log; select another parser/template pair via `LILITH_SERVE_TOOL_PARSER` / `LILITH_SERVE_CHAT_TEMPLATE` in the pod env |
| `serve_pod.sh` fails with `lilith::serve::reasoning_parser` | An *explicit* `LILITH_SERVE_REASONING_PARSER=<name>` isn't registered in this vLLM | Pick a listed name, `auto` (best-effort), or `none` (disable it outright) |
| `start`/`wait-ready` exit 5 `lilith::serve::health_timeout` | vLLM not healthy in 30 min; `start` stops the pod | `ssh` in, read `serve/status.json` and `serve/sessions/<latest>/` and the vLLM log |
| `status.json` `failed` with `lilith::serve::bootstrap` | Parent/driver/CUDA check failed (not auto-repaired) | Fix the volume, or recreate on a CUDA 13 host |
| `status.json` `failed` with `lilith::serve::auth` | `/v1/models` answered without the key | Never serve like that (the proxy is public); check vLLM's `VLLM_API_KEY` handling |
| `status.json` `failed` with `lilith::serve::provenance` | Payload files ≠ manifest ≠ `current.json` main SHA | Reinstall a payload built from origin/main |
| Supervisor log `STOP FAILED` | The stop call failed; the session stays open and bills | The idle-watch retries every minute; if it persists, stop in the console |
| `idle-watch` adopted a pod | Someone started it outside the supervisor | Normal: it is now under the cap and idle stop |
| `create` fails at the 1Password write | op could not store the key or endpoint | Create the item by hand (API Credential, 64 random chars) and rerun `create`, which reuses it; `sync-endpoint` retries the endpoint write |

### Shared env on the volume

The CUDA env at `/workspace/lilith/env` is shared with training pods. When `serve_pod.sh` finds an
env built from a different lock, it moves the env aside (`env.old-<ts>`) and rebuilds it from the
payload's lock (C6 round-3 lesson). **Do not start the serve pod while a training pod on the same
volume runs with a different lock.** Payloads from the same main SHA share the lock, so they never
conflict.

## Secrets checklist

- Nothing secret on argv. The Runpod key goes to `curl`/urllib in memory or on stdin (`-H @-`);
  the serve key goes to op on stdin and to vLLM through the environment.
- `--key-source runpod-secret` writes `{{ RUNPOD_SECRET_lilith_serve_api_key }}` into the pod env
  instead of the value. It needs a Runpod secret with that name and the 1Password value. Creating
  that secret is a new Runpod resource and therefore an operator action. Default: the value in
  the pod env, visible to account members in the console.
- The pod's own `RUNPOD_API_KEY` (pod-scoped, injected by Runpod) is used only by the on-pod
  backstop to stop itself.

## Tests

```sh
python3 -m unittest scripts/lilith/serve/test_lilith_serve.py   # 46 tests, ~60 s, CPU only
python3 -m unittest scripts/lilith/runpod/test_runpod_scripts.py
```

A local HTTP server mocks the Runpod REST/GraphQL APIs and the pod's vLLM proxy, and a fake
`op` stands in for 1Password. The tests cover budget refusal (weekly, monthly share, reserve),
idle stop, in-flight activity, unreachable metrics, session cap (including a shortened cap),
stop-failure retry, external stop, adoption, and stable-URL bookkeeping across repeated
stop/start. They also cover zero-GPU resume, health timeout, recreate as the only URL change, and
no secret in stdout, logs, state or op argv. `serve_pod.sh` runs against a fake vLLM: parent and
adapter modes, key enforced, bodies redacted, refusals.
